# Способы тестирования BenchCode

**Версия:** 2.0  
**Статус:** рабочая версия, согласованная с актуальными требованиями системы  
**Дата актуализации:** 2026-11-12

## 1. Назначение и основания

Документ описывает методы, уровни и техники тестирования BenchCode. Он задаёт способ получать проверяемые свидетельства соответствия функциональным сценариям и нефункциональным требованиям, но сам по себе не вводит новые требования к продукту.

Источники требований: [Функциональные требования](./Функциональные%20требования.md), [Нефункциональные требования](./Нефункциональные%20требования.md), [MoSCoW-приоритизация](./Приоритизация%20по%20MoSCoW.md), [диаграмма классов](./classDiagram.mermaid), [C4-модель](./c4.c4). Полный контекст запуска и критерии приёмки приведены в [Плане тестирования проекта](./План_тестирования_проекта.md).

Планирование использует сценарии UC и трассировку требований в духе RUP; тест-дизайн опирается на общепринятые техники тестирования. Это практическая структура проекта, а не заявление о сертифицированном соответствии конкретному стандарту.

## 2. Объект тестирования и границы

Проверяются:

- веб-интерфейс Compose Multiplatform/WASM и его статическая раздача;
- REST API и проверка токенов/прав;
- модули аутентификации и соревнований;
- хранение сущностей `ApplicationUser`, `Competition`, `Participation`, `Task`, `Test`, `Submission`, `TestResult` в PostgreSQL;
- RabbitMQ и взаимодействие API с воркером;
- компиляция и запуск C++, Python, Java и C# в Docker Runtime;
- вычисление результатов и рейтинга, история посылок и экспорт CSV (Should have);
- пользовательские сообщения, ограничения данных, обработка ошибок и очистка ресурсов.

Не входят в объём MVP и не должны случайно становиться критериями приёмки: глобальные роли «студент/преподаватель», пароль соревнования, каталог чужих соревнований, rejudge старых посылок, автоматическое восстановление пароля, мобильные приложения, резервное копирование, SLA и многоузловые воркеры.

## 3. Уровни тестирования

| Уровень | Цель | Примеры для BenchCode |
|---|---|---|
| Модульный | Проверить изолированную бизнес-логику | Нормализация email; проверка правил пароля; вычисление late-флага; рейтинг и общие места; сравнение текстового вывода |
| Компонентный | Проверить один модуль с контролируемыми зависимостями | Регистрация; создание/публикация соревнования; изменение версии; валидация тестов; формирование ответа посылки |
| Интеграционный | Проверить контракты между реальными компонентами | API–PostgreSQL; API–RabbitMQ; воркер–БД; воркер–Docker Runtime; интерфейс–API |
| Системный / E2E | Проверить пользовательский путь через развернутую систему | Пользователь создаёт соревнование, добавляет задачу, публикует код; другой пользователь присоединяется, отправляет решение и видит результат |
| Приёмочный | Подтвердить бизнес-сценарии и Must/NFR | Проверка UC-01…UC-14, защиты скрытых тестов, рейтинга, отказов и лимитов по согласованным критериям |

Проверки разделяются по уровню так, чтобы бизнес-правила быстро проверялись модульно, межкомпонентные сбои — интеграционно, а ключевые пользовательские потоки — сквозными тестами.

## 4. Виды и методы проверок

| Вид проверки | Что подтверждает | Применение |
|---|---|---|
| Функциональное | Соответствие основным и альтернативным потокам UC | Регистрация, присоединение, управление, задачи, отправка и результаты |
| Проверка авторизации | Объектные права и запрет доступа | `Owner` и `Participant` проверяются на сервере для соревнования, задачи, теста, посылки и рейтинга |
| Проверка валидации | Принимаются только допустимые данные | Email, пароль, код, язык, лимиты, обязательный ожидаемый вывод, форма чекера |
| Проверка вердиктов | Правильная классификация результата | `AC`, `WA`, `CE`, `RE`, `TLE`, `MLE`; отдельно `SystemError` |
| Проверка безопасности | Защита данных, доступа и среды исполнения | Скрытые тесты не раскрываются; контейнер ограничен; пароль/секреты не логируются; права проверяются сервером |
| Проверка отказоустойчивости | Согласованность при отказе зависимостей | Недоступность БД, RabbitMQ, воркера или Docker Runtime; сохранение принятой посылки и ручное восстановление системной ошибки |
| Нагрузочная | Выполнение заданного профиля читающих операций | Не менее 30 RPS, API p95 не более 300 мс при измеренном и зафиксированном профиле |
| Производительности интерфейса | Время отклика интерактивных операций | p95 не более 1.5 с в уже загруженном приложении; полный цикл проверки решения не нормируется |
| Ёмкости | Работа с предельным объёмом данных | Не менее 50 000 посылок с результатами по тестам; проверка квот данных |
| Совместимости | Работа в поддерживаемых браузерах и размерах экрана | Две последние мажорные версии Chrome, Firefox, Safari, Яндекс.Браузера с WasmGC; ширина 360–1920 px |
| Удобства использования | Понятность и завершимость ключевого пути | Решение задачи в едином рабочем экране, видимые статусы и конкретные сообщения |
| Регрессионная | Отсутствие повторного появления исправленных ошибок | Запуск набора критических тестов после изменений API, рейтинга, модели данных и воркера |
| Исследовательская | Поиск неожиданных сочетаний и дефектов | Ограниченные по времени сессии с заранее заданной целью и фиксацией исследованных областей |

## 5. Техники тест-дизайна

### 5.1 Классы эквивалентности и граничные значения

Для каждого лимита проверяются допустимые значения, нижняя/верхняя граница и первое значение за границей. Размеры файлов и кода измеряются в байтах, а не в количестве символов.

| Область | Границы и классы |
|---|---|
| Код соревнования | 6 допустимых символов Base32 без `0`, `1`, `I`, `O`; длина 5/6/7; символы вне алфавита |
| Пароль | 7/8 символов; только строчные; только заглавные; обе категории; цифры и спецсимволы не обязательны |
| Неудачные входы | 4/5/6 попыток в пределах 15 минут; проверить ограничение на учётную запись и IP |
| Присоединение и посылки | 9/10/11 попыток присоединения за минуту; 5/6/7 посылок за минуту |
| Исходный код | Пустое значение; 64 КБ; более 64 КБ; язык разрешён/не разрешён |
| Тесты | 0/1/100/101 тест; файл 1 МБ и больше; суммарный объём 10 МБ и больше |
| Квоты | 49/50/51 задач; 19/20/21 активное соревнование |
| Время | Дедлайн не задан; до дедлайна; ровно на границе; после дедлайна; разные локальные часовые пояса |
| Производительность | Фиксировать объём набора, конкурентность, профиль операций и прогрев; сравнивать p95 с конкретным NFR |

Граничный тест не должен подменять полноценную нагрузочную проверку: например, наличие 50 000 посылок проверяется отдельно от скорости API.

### 5.2 Таблицы решений

Таблицы решений подходят для комбинаций, где результат зависит от нескольких условий:

- доступ к чужому коду: право пользователя × дедлайн × флаг `AllowViewOthersCode`;
- включение в рейтинг: версия посылки × late-флаг × наличие `AC` × наличие успешно решённой задачи;
- доступ к объекту: объект существует × токен действителен × пользователь `Owner`/`Participant`;
- публикация: есть задача × тесты валидны × checker настроен корректно;
- видимость результата теста: публичный/скрытый × пользователь участник/организатор.

Для каждого набора условий фиксируются ожидаемые права, сообщение и состав возвращаемых данных.

### 5.3 Тестирование переходов состояний

Проверяются разрешённые переходы и отсутствие некорректных переходов:

- соревнование: `Draft` → `Published` → `Archived`; публикация без задачи запрещена;
- полная посылка: сохранение со статусом `Testing` → `Finished` с вердиктом либо `SystemError` при сбое платформы;
- проверка: компиляция при необходимости → выполнение тестов → запись результатов → удаление контейнера;
- изменение параметров сравнимости → увеличение версии → рейтинг по текущей версии; прежние посылки остаются в истории и автоматически не перепроверяются.

### 5.4 Проверка результатов по эталону

Для рейтинга создаётся небольшой заранее рассчитанный набор участников и посылок. Ожидаемый результат независимо рассчитывается вручную по BR-31:

1. Исключить посылки не текущей версии, с опозданием и без `AC`.
2. Выбрать лучшую успешную посылку участника по каждой задаче согласно правилам проекта.
3. Рассчитать число решённых задач, нормированные показатели времени/памяти и сумму взвешенных показателей.
4. Проверить сортировку и общее место при равенстве.

Не использовать медиану: текущая формула рейтинга задаёт число решённых задач и сумму взвешенных нормированных метрик.

### 5.5 Комбинации и воспроизводимость

Комбинирование языков, типов checker, видимости тестов, дедлайнов и статусов строится по риску. Парное покрытие допустимо для низкорисковых сочетаний, но не заменяет обязательные проверки каждого языка, каждого вердикта, прав доступа и утечки скрытых данных.

Измерения времени/памяти выполняются с фиксацией состава тестов, языка, версии образа и конфигурации машины. Разброс измерений документируется; норматив на число прогревов, повторов или процент разброса не задан и не должен вводиться без согласования.

## 6. Подход к проверке отдельных подсистем

### 6.1 Аутентификация и авторизация

- Проверить нормализацию email, уникальность и правила пароля, обязательное согласие и фиксацию версии политики.
- Проверить выдачу access/refresh токенов и серверную проверку действительности на каждом защищённом запросе.
- Проверить предел входа 5 неудачных попыток за 15 минут и единое сообщение при неверных данных.
- Создать минимум два тестовых аккаунта и проверить, что замена идентификатора объекта не даёт доступ к чужому соревнованию, задаче или посылке.
- Убедиться, что `Owner` не является глобальной ролью, а код соревнования не выдаёт права управления.
- Проверить `401`, `403`, `404` в соответствии с архитектурной моделью.

### 6.2 Соревнования, задачи и тесты

- Проверить создание черновика, уникальность 6-символьного кода, публикацию только после добавления валидной задачи и идемпотентное присоединение.
- Проверить дедлайн в UTC, отображение в локальном часовом поясе и сравнение по времени сервера.
- Проверить лимиты задач, файлов, тестов, кодов чекера и разрешённых языков.
- Проверить рост версии при изменении задач, тестов, лимитов, checker, языков и весов; не увеличивать версию для полей, которые по требованиям не меняют сравнимость.
- Проверить запрет удаления при наличии посылок и возможность архивации.

### 6.3 Исполнение и вердикты

Для каждого поддерживаемого языка использовать небольшой контролируемый набор программ, который даёт известные результаты:

- корректное решение (`AC`);
- корректно компилируемое, но неверное решение (`WA`);
- ошибка компиляции (`CE`) для компилируемых языков;
- ошибка выполнения (`RE`);
- превышение времени (`TLE`);
- превышение памяти (`MLE`);
- искусственно вызванный сбой тестовой инфраструктуры (`SystemError`).

Проверять отдельно полный прогон и запуск только на публичных тестах. Для последнего подтверждать отсутствие записи в реестре посылок. Проверки Docker выполняются только в выделенной тестовой среде с безопасными тестовыми программами, без использования продуктивной инфраструктуры.

### 6.4 Защита данных и результаты

- Сравнить ответы API для участника и организатора: участник не получает содержимое скрытых тестов, эталоны или diff; организатору доступ разрешён.
- Проверить, что коды посылок, входные данные и исходный код не появляются в неавторизованных ответах.
- Проверить, что строки вывода при `WA` формируются только для публичных тестов и ограничены 1000 строками.
- Проверить видимость чужого кода до/после дедлайна, с флагом и без него, а также доступ организатора.
- Проверить включение посылок в таблицу результатов и CSV по текущей версии и late-флагу.

### 6.5 Нефункциональные проверки

| NFR | Метод | Измеримый критерий |
|---|---|---|
| NFR-001 | Анализ конфигурации, тесты доступа и Docker, проверка ответов/логов | HTTPS TLS 1.2+; правила пароля/токенов/лимитов; ограничения контейнера; отсутствие утечки скрытых тестов |
| NFR-002 | Измерение действий в загруженном приложении | p95 интерактивных операций ≤ 1.5 с; первичная загрузка WASM и полный цикл вердикта исключены |
| NFR-003 | Нагрузочный профиль читающих и интерактивных API | ≥ 30 RPS и API p95 ≤ 300 мс; зафиксировать профиль и состав запросов |
| NFR-004 | Сценарная оценка и проверка сообщений | Задача решается в едином экране; статусы и ошибки соответствуют требованиям |
| NFR-005 | Набор данных и проверки граничных квот | Не менее 50 000 посылок с результатами; проверка размеров хранения и ограничений данных |
| NFR-006 | Матрица поддерживаемых браузеров и размеров | Две последние мажорные версии заданных браузеров с WasmGC; 360–1920 px |
| NFR-007 | Сценарии отключения/перезапуска зависимостей и контроль контейнеров | Принятая посылка сохранена; системный сбой не становится `TLE`; контейнеры очищены |

Uptime, резервное копирование, p95 полного цикла проверки, процент разброса замеров, точный интервал опроса и точный профиль параллелизма не являются утверждёнными порогами в текущих NFR.

## 7. Дефект и запись результата

Для каждого прогона фиксировать:

- ID теста и ссылки на UC/BR/NFR;
- сборку приложения, версии конфигурации и образов языков;
- предусловия, тестовые данные и шаги;
- ожидаемый и фактический результат;
- статус (Passed / Failed / Blocked / Not run);
- окружение, время выполнения и вложения без секретов/скрытых тестовых данных.

Для дефекта указывать шаги воспроизведения, ожидаемое/фактическое поведение, серьёзность, приоритет, частоту воспроизведения и связь с требованием. Не включать реальные пароли, токены, персональные данные или содержимое скрытых тестов.

**Серьёзность:**

- **Критическая:** обход объектной авторизации, раскрытие скрытых тестов, выполнение кода вне изоляции, потеря/подмена результатов посылок.
- **Высокая:** неверный вердикт, неверный рейтинг, недоступен ключевой сценарий Must, лимит ресурса не применяется.
- **Средняя:** неверная обработка альтернативного потока, ошибка представления данных без нарушения их целостности.
- **Низкая:** косметическое несоответствие без влияния на сценарий и корректность.

Приоритет исправления определяется риском, охватом пользователей и наличием обходного пути; серьёзность и приоритет не следует смешивать.

## 8. Автоматизация и ручное тестирование

Автоматизировать в первую очередь стабильные детерминированные проверки: бизнес-правила, валидацию, права доступа, версии, рейтинг, форматы ответов, лимиты и основные API/E2E-потоки. Для проверки контейнера и отказов автоматизация выполняется только в изолированном окружении.

Ручные проверки использовать для исследовательского тестирования, удобства использования, визуальной адаптивности, проверки браузеров и диагностики сложных отказов. Изменения, закрывающие дефект, сопровождаются регрессионной проверкой и, где возможно, автоматизированным тестом.

Документ не предписывает конкретный тестовый фреймворк: стек проекта не фиксирует выбор такого инструмента.
