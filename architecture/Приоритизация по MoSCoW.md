# Приоритизация по MoSCoW

Приоритеты присвоены согласованной модели (файл в базе знаний — прежняя версия документа; его устаревшие пункты не переношу, перечень исключений — в конце раздела). Нумерация соответствует каталогу UC-01…UC-15, реестру BR-01…BR-38 и NFR-001…NFR-007.

## Принципы приоритизации

- **Must have** — минимальный работоспособный контур: без него сценарии не выполняются либо теряется смысл системы (проверка в изоляции, защита скрытых тестов, объектная авторизация).
- **Should have** — важно для удобства и отчётности, но существует обходной путь; указывается явно.
- **Could have** — реализуется при остатке ресурса, не влияет на Must.
- **Won't have** — сознательно вне объёма MVP.
- Если сценарий имеет приоритет Must, все шаги его основного потока обязательны; расширения могут иметь отдельный приоритет.
- Все NFR-001…NFR-007 — Must have.

---

## Must have

**M1. Учётные записи и доступ — UC-01, UC-14; BR-01…BR-06, BR-38; NFR-001**
Регистрация (имя, фамилия, email, пароль, согласие на обработку персональных данных; без ролей и учебной группы). Вход по email и паролю; пароль не менее 8 символов с обязательными строчной и заглавной буквами; хранение только необратимого хеша. Токены доступа (30 минут) и обновления (14 дней) с серверной проверкой. Блокировка после 5 неудачных попыток за 15 минут. Восстановление доступа через владельца развёртывания. Объектная авторизация: права `Owner` / `Participant` проверяются на каждом запросе.

**M2. Единая главная страница — UC-11; BR-07, BR-08, BR-13, BR-36**
Списки «Я организатор» и «Я участвую», карточки с названием, дедлайном, числом задач и статусом, фильтрация своих соревнований по тегу группы, постоянные действия «Присоединиться по коду» и «Создать соревнование». Переключатели режима и отдельные версии интерфейса отсутствуют.

**M3. Присоединение по коду — UC-02; BR-10…BR-13, BR-15, BR-34**
Ввод кода из 6 символов, идемпотентное создание права `Participant`, единое сообщение для ненайденного, неопубликованного и архивированного соревнования, лимит 10 попыток в минуту.

**M4. Просмотр соревнования и задач — UC-03; BR-16…BR-19, BR-22**
Карточки задач в порядке номеров, статусы текущего пользователя (Новая, Тестируется, Решена, Ошибка с типом вердикта), дедлайн в локальном часовом поясе, баннер об истечении срока и метки «Сдано вовремя» / «Сдано с опозданием», отображение текущей версии соревнования.

**M5. Отправка решения и проверка — UC-04, UC-10; BR-21…BR-30, BR-34, BR-35; NFR-001, NFR-005**
Единый экран задачи: условие в Markdown, публичные тесты только для чтения, выбор языка из разрешённых, редактор с подсветкой синтаксиса, отображение лимитов. Проверка на публичных тестах без сохранения. Полная посылка: сохранение в БД до постановки в очередь со статусом «Тестируется», прогон на всех тестах, вердикты AC / WA / CE / RE / TLE / MLE, отдельный исход «системная ошибка» при сбое инфраструктуры. Метрики — максимум времени и памяти по тестам. Вывод при AC не сохраняется; при WA сохраняется различие вывода не более 1000 строк и только по публичным тестам. Обновление результата без перезагрузки, вывод компилятора при CE. Ограничения: код 64 КБ, 6 посылок в минуту, изоляция окружения, лимиты компиляции 30 с и 2 ГБ. Скрытые тесты, их входные данные и эталоны участнику не возвращаются.

**M6. Результаты и рейтинг — UC-05; BR-18, BR-19, BR-30…BR-33, BR-36…BR-38; NFR-002, NFR-003**
Расчёт на лету: только текущая версия соревнования, без посылок «с опозданием», лучшие успешные посылки по каждой задаче. Ранжирование по числу решённых задач, затем по взвешенной сумме нормированных показателей времени и памяти; при равенстве — общее место. Средние показатели по участникам соревнования. Видимость чужого кода: после дедлайна или при включённом флаге, организатору — всегда.

**M7. Управление соревнованием и задачами — UC-06, UC-07, UC-08, UC-13; BR-09, BR-14…BR-17, BR-19, BR-20, BR-25, BR-26, BR-29, BR-34**
Панель управления по праву `Owner`, без пароля управления. Создание соревнования: черновик → задачи → публикация; обязательное название, необязательные дедлайн и тег группы, веса критериев (0.5 и 0.5), флаг просмотра чужих решений, лимиты по умолчанию, код-идентификатор из 6 символов, ссылка-приглашение. Задачи: порядковый номер, условие в Markdown с предпросмотром, лимиты времени и памяти, разрешённые языки, способ проверки (сравнение с текстом или программа-чекер с обязательным выбором языка), тесты с номером и признаком публичности (файл ≤ 1 МБ, ≤ 10 МБ на задачу, ≤ 100 тестов). Увеличение версии при изменении параметров сравнимости. Удаление только при отсутствии посылок, иначе архивация. Настройки соревнования и список участников (имя, фамилия, дата присоединения).

**M8. Реестр посылок и история — UC-09, UC-12; BR-09, BR-21, BR-22, BR-27, BR-28, BR-30, BR-38**
Реестр организатора: все полные посылки задачи, включая находящиеся в статусе «Тестируется» и завершённые системной ошибкой, с метками версии и опоздания, фильтрами и постраничной навигацией; карточка посылки с исходным кодом и деталями по тестам, данные скрытых тестов доступны организатору. Раздел «Мои посылки»: история по всем соревнованиям, фильтры, карточка, повторная отправка.

**M9. Платформенные требования — NFR-001…NFR-007**
HTTPS, изоляция исполнения, лимиты и квоты, защита скрытых тестов. p95 ≤ 1.5 с на интерактивные операции в загруженном приложении; не менее 30 RPS на чтение при p95 ответа API ≤ 300 мс. Единый экран задачи, единый набор статусов, конкретные сообщения об ошибках, компоненты Material 3. Ёмкость не менее 50 000 посылок, хранение тестов в БД. Адаптивность 360–1920 px, две последние мажорные версии четырёх браузеров, поддержка WasmGC. Сохранность принятых посылок до постановки в очередь, разделение системной ошибки и вердиктов о превышении лимитов, освобождение окружений после прогона.

## Порядок реализации (зависимости)

1. UC-01 и объектная авторизация (основа для всех проверок прав).
2. UC-11, UC-07, UC-08, UC-06 — появление контента: соревнования, задачи, тесты.
3. UC-02, UC-03 — доступ участников и просмотр задач.
4. UC-04 и UC-10 — отправка, очередь, изолированный прогон, вердикты и метрики.
5. UC-05 — рейтинг на накопленных данных.
6. UC-09, UC-12 — реестр и история.
7. UC-13 — настройки, версия, архивация, участники; UC-14 — процедура восстановления доступа.
8. Should: UC-15 и расширения представлений; затем Could.

**Примечание об объёме.** Must охватывает 14 из 15 сценариев и все NFR. Если ресурс команды не позволяет, кандидаты на пересмотр приоритета: сравнение со средними показателями (UC-05, шаг 6), фильтрация по тегу группы (UC-11, шаг 3), список участников (UC-13, шаг 4), расширенные фильтры реестра (UC-09, шаг 3). Ядро — UC-01…UC-05, UC-07, UC-08, UC-10 — понижению не подлежит.

## Не переносить из предыдущей версии документа

Выбор режима и роли «студент» / «преподаватель»; мастер-пароль соревнования и вход по нему; регистрация и авторизация в разделе Could have; ввод ФИО в форме посылки; медианные показатели и ранжирование по медианам; норматив uptime и допустимый downtime; обоснования по категориям стандарта качества; формулировка «весь сценарий на одной странице»; статус «В очереди»; три отдельные базы данных и префикс `/api/v1`; наименование CodeBench; ссылки на исследования без данных и неформальные комментарии.
