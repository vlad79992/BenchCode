# Руководство разработчика

## Где находится Kotlin-код

```text
BenchCode.ComposeWebApp/
├── project.yaml                 # модули Amper
├── libs.versions.toml           # версии сторонних библиотек
├── shared/
│   ├── module.yaml              # общие зависимости и targets
│   ├── src/                     # общий Kotlin и Compose UI
│   ├── src@android/             # Android actual-код
│   ├── src@jvm/                 # JVM actual-код
│   ├── src@wasmJs/              # Wasm JS actual-код
│   ├── test/                    # общие тесты
│   ├── test@android/
│   ├── test@jvm/
│   └── test@wasmJs/
├── androidApp/                  # Android-приложение и MainActivity
├── desktopApp/                  # desktop entry point и ресурсы
└── webApp/                      # Wasm JS entry point и web-ресурсы
```

Внутри `shared/src` код сгруппирован по ответственности: `data/` — модели и репозитории, `di/` — Koin-модули, `navigation/` — маршруты и back stack, `shared/` — общие экраны, `student/` — сценарии студента, `*ViewModel.kt` — состояние экранов.

## Добавление UI и поведения

1. Разместите composable-экран в подходящем пакете `shared/src` и держите бизнес-/экранное состояние в ViewModel, если оно должно переживать recomposition или асинхронное обновление.
2. Для нового маршрута добавьте сериализуемый тип `NavKey` в подходящий sealed route-интерфейс в `navigation/`.
3. Зарегистрируйте ViewModel и сопоставление маршрута с экраном в `di/AppModule.kt`.
4. Добавьте действие перехода, используя `LocalNavBackStack`, и проверьте начальный back stack в `NavigationRoot`.
5. Если функциональность зависит от платформы, определите общий `expect`-контракт и реализации в соответствующих `src@android`, `src@jvm` и `src@wasmJs`. Не размещайте Android/JVM/Web API в common source set.
6. Если добавилась новая библиотека, обновите `libs.versions.toml` и manifest нужного модуля `module.yaml`; затем проверьте все targets, где модуль собирается.

Для нового самостоятельного компонента сначала определите, должен ли он принадлежать общей библиотеке `shared` или только одному app-модулю. Новый модуль также нужно добавить в `project.yaml` и связать зависимостями в соответствующих `module.yaml`.

## Локальная проверка

Из `BenchCode.ComposeWebApp`:

```shell
./kotlin build
./kotlin test
```

При ограниченном цикле проверяйте только изменённый модуль через `-m`, например `./kotlin test -m shared`. UI дополнительно проверьте на целевом запуске: `./kotlin run -m webApp`, `desktopApp` или `androidApp`. Если изменение касается общего кода, не ограничивайтесь проверкой только одной платформы.

## Стиль и соглашения

- Держите общие типы в `org.codebench.composewebapp` и его функциональных подпакетах; платформенные реализации размещайте в соответствующих platform source sets.
- Для новых типов используйте `PascalCase`, для функций и свойств — `lowerCamelCase`, для констант — существующее соглашение файла/пакета. В текущих моделях есть исторические исключения (например, PascalCase свойства `Task`); не копируйте их автоматически в новый код.
- Предпочитайте небольшие composable-функции и передавайте состояние/события через ViewModel или параметры, не смешивая платформенную инфраструктуру с отображением UI.
- Регистрируйте зависимости через Koin-модули, а не создавайте инфраструктурные объекты в composable при каждой композиции.
- Для публичного API добавляйте осмысленные KDoc-комментарии. Dokka покажет документированные публичные объявления и соответствующие multiplatform targets.
- Сохраняйте языковые соглашения существующих экранов и не смешивайте рефакторинг оформления с функциональным изменением без необходимости.

## Важное ограничение текущего прототипа

Экраны соревнований пока показывают переданный код соревнования, а функциональность роли преподавателя и сетевой загрузки не реализована. Планируя новую функциональность, сначала согласуйте контракт и интеграцию с соответствующими сервисами; не исходите из того, что их API уже вызывается приложением.
